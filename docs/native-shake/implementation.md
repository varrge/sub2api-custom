# 原生摇摇乐（Lucky Box）实现说明

摇摇乐现在完全由 Sub 自己实现，不再依赖卡网（KaWang）服务器。本文是这套实现的权威说明；改动前请先读。

本改动本身不会部署、不会启用任何活动、也不会发卡。迁移只建表。

## 范围

替换的卡网代码：`kwRedeem/api/src/sub2api-shake.js`（活动、发卡、抽奖）、`sub2api-shake-rewards.js`（消费榜发卡）、`sub2api-activity-cards.js`（双十一任务卡），以及 Sub 里转发到卡网的 `internal/handler/native_box.go`（已删除）。

不在范围内：卡网独有的 Boss 讨伐摇摇卡奖励（`sub2api-raid.js`）没有对应的 Sub 功能，无法在 Sub 内适配。卡网的历史活动、卡片、进度和抽奖记录不导入，新系统从零开始；需要补偿的用户请在后台手动补发。

## 活动生命周期

活动有三个存储状态：`draft`、`active`、`ended`。页面上显示的“待开始/进行中”由存储状态和时间推出。

草稿不发卡，用户看不到。启用时检查时间窗口，同一时间只能有一个已启用活动（窗口不能重叠），这样一张订单或一笔消耗不会被两个活动同时计算，用户页也只有一个活动可显示。启用后开始时间锁定，结束时间只能改到未来；发卡规则的来源、类型、分组和计算方式锁定，不能增删规则；阈值、张数、卡种、奖池和权重可以继续修改，每次保存生成一个新的配置版本（`shake_config_versions`），抽奖记录保存它使用的版本。保存时带上 `config_version` 做乐观锁，两个管理员同时编辑时后保存的一方会收到冲突提示。

到期后后台任务先按截止时间做最后一次发卡，在最终行锁内重新检查截止时间，确认未被延期后再把活动标为结束，并把未使用的卡作废。管理员也可以提前结束（需填写原因）。只有从未启用的草稿可以删除。

## 发卡规则（后台可自定义）

每条规则包含来源、范围、发卡方式、张数和卡种（低/中/高）：

| 来源 | 说明 | 发卡方式 |
| --- | --- | --- |
| 订单 `order` | 已完成（`COMPLETED`）的支付订单，按 `completed_at` 落在活动时间内。订单类型可选订阅、月卡、余额充值 | 每笔订单固定张数（`per_order`），或按订单金额累计满额（`threshold`） |
| 实际消耗 `usage` | `usage_logs.actual_cost`，按 `created_at` 落在活动时间内。计费类型可选余额消耗（`billing_type=0`）或订阅额度消耗（`billing_type=1`，包含没有 `subscription_id` 的原生月卡） | 累计满额 |

金额单位沿用订单的记账口径：月卡订单为人民币（CNY，页面显示 ¥），余额充值为到账美元（含赠金），订阅为套餐 `price` 的美元记账数值；支付渠道实收 `pay_amount` 不用于发卡。实际消耗和余额奖品均为美元。累计规则不跨订单类型合计，也不临时换汇。

规则可以指定分组 ID（订单用 `subscription_group_id`，消耗用 `usage_logs.group_id`）。不填分组的规则是兜底规则，会自动排除同类规则里已单独配置的分组，所以一行数据最多被一条规则计算。这与卡网“指定分组规则 + 全部兜底规则”的做法一致。

与卡网的刻意差异：

- 累计规则不靠游标逐条累加，而是每次从 `usage_logs` / `payment_orders` 重新汇总，再和 `shake_progress.units`（已经发过几个阈值）比较。迟到写入的消耗、恢复后的月卡账单都不会漏算。`units` 只增不减，所以退款、删除记录或修改阈值都不会收回已发的卡。
- 启用后锁定规则的来源、类型、分组和发卡方式，不能增删规则，避免改变范围或计算方式后重新奖励同一笔历史消费；阈值调低仍会按新阈值补发差额。
- 按单规则用 `shake_order_credits` 记录“这个活动已经为这笔订单发过卡”。之后改张数或卡种，只影响新订单。
- 与消费榜相同，仍在 `month_card_billing_pending` 里的消耗暂不计入，恢复后再计入。
- 只统计正常状态的个人账号；企业账号、已禁用和已删除的账号不发卡。

发卡由后台任务每 5 分钟对全部用户执行一次（每类来源只汇总扫描一次 `usage_logs` / `payment_orders`，再在内存里按规则分配）；用户打开开箱页时会立即为他自己执行一次，所以刚购买或刚消耗后刷新页面就能看到新卡。管理员也可以在后台点“立即发卡”。所有发卡都用确定的 `source_ref` 加唯一约束去重。锁的设计：全量发卡持有活动级排他锁；用户发卡持有活动级共享锁加该用户的排他锁，所以不同用户打开页面互不阻塞，同一用户并发刷新也不会重复发卡；拿不到锁的那次直接跳过，由下一次补上。活动到期时的最后一次发卡会等待锁而不是跳过，保证截止前写入的消耗都被计算。单个用户、单条规则一次最多新增 200 个阈值单位，防止误配极小阈值时一次写入过多。

## 抽奖

抽奖、扣卡、发奖在同一个数据库事务里完成，结果要么完整记录，要么什么都没发生：

1. 按用户加事务锁；同一 `requestId` 已有记录时直接返回原结果（活动或卡种不一致则拒绝），不会再扣卡。
2. 活动必须处于进行中，用户必须是正常个人账号。
3. 取一张该卡种的可用卡（`FOR UPDATE SKIP LOCKED`），按该卡种的权重用加密随机数选奖品。
4. 写抽奖记录并消耗卡片。余额奖品直接加到 `users.balance`，并在 `redeem_codes` 写一条类型为 `shake_balance` 的余额记录（不计入充值统计和邀请返利）；“再来一次”发一张同卡种的新卡。
5. 提交后刷新该用户的余额与鉴权缓存。

余额奖品在用户页和后台的余额记录里显示为“余额奖励（摇摇乐）”，作废扣回显示为“奖励扣回（摇摇乐作废）”，并附带活动、奖品和抽奖编号。

因为发奖与抽奖同事务，卡网的 `selected` / `delivery_failed` 状态和“重试发放/确认已发放”处置已经不需要。抽奖记录只有 `delivered` 和 `voided` 两种状态。用户页原有的“同一 requestId 重试/恢复”逻辑保持不变：恢复接口只查不抽；恢复查询会等待同一用户正在执行的抽奖，以及该活动正在提交的配置修改。请求从未到达服务器时，只有在活动结束后，或该活动在 Sub 里根本不存在时（例如浏览器里残留的卡网时期请求），才返回 `closed_without_draw`。

管理员可以作废一条抽奖记录（需填写原因）：扣回该次发放的余额（余额可能变成负数），并作废尚未使用的“再来一次”卡；已消耗的抽奖卡不退回。

## 消费榜自动发卡

后台“消费榜自动发卡”把当前消费榜活动（设置 → 消费榜）绑定到一个摇摇乐活动。绑定时快照消费榜的奖励规则和指纹，并检查：消费榜已开启自动奖励；按天结算时起止时间都在北京时间零点；摇摇乐活动覆盖消费活动开始时间，并在最后一次结算（结束时间 + 结算延迟）之后至少保留 24 小时；同一消费活动或重叠的统计日期只能有一个任务。

每个周期结束并过了结算延迟后，后台任务调用 Sub 已有的冻结接口（`activity_reward_manifests`）取得名单，按任务自己的规则快照重新核对每一名的卡种和张数（排名连续、金额递减、零消耗只得参与奖），核对通过才在一个事务里发卡并写入 `shake_reward_days`，每个周期只发一次。冻结后被删除或转为企业账号的用户跳过。任何失败都写入任务的 `last_error`，下一分钟自动重试。消费活动开始前可以“同步奖励规则”重新快照，开始后锁定。

## 双十一任务卡

三弹活动的“目标摇摇卡活动 ID”现在填写摇摇乐后台里的活动 ID（`shake-` 开头）。启用双十一活动时检查该摇摇乐活动存在、已启用、开始不晚于双十一活动、结束不早于要求的时间（第二弹另需最长招募期 + 24 小时）。

领取任务奖励时直接在本地发卡（`GrantActivityTask`），按“活动/用户/任务”去重，重复领取或网络重试不会多发；摇摇乐活动未开启或已结束时奖励保持未发放，可以之后重试。`activity_campaign_rewards.connection_id` 新记录固定写 `native`。

切换现有活动时，仅允许将不存在于本地摇摇乐表的旧目标一次性重绑到已校验的本地活动；已有参与记录的起止时间仍不可修改，本地活动之间不可再次重绑。配置和未发放奖励的目标、连接 ID 在同一事务中更新；已发放记录保留原目标与发放时间，领取时直接返回成功，不在原生系统补发。判断目标归属用数据库记录，不能依赖 `shake-` 前缀（旧卡网 ID 也使用此开头）。

## 接口

用户（需登录，仅个人账号）：`GET /api/v1/activities/box/bootstrap`、`POST /api/v1/activities/box/draws`、`POST /api/v1/activities/box/draws/recover`。响应字段与原卡网网关一致，`connectionId` 固定为 `native`；`progress` 改为新的规则说明格式。

后台（`/api/v1/admin/shake`）：活动列表/创建/详情/保存/启用/结束/删除草稿/立即发卡、手动补发、查看用户卡片、抽奖记录与作废、消费榜任务的创建/暂停/重试/同步规则。保存配置、启用、结束、补发、作废，以及创建/暂停消费榜任务和同步规则都需要 TOTP 二次验证。所有管理操作写入 `shake_audit`。

## 上线步骤

1. 停掉卡网摇摇乐：结束卡网上对这台 Sub 的进行中活动、暂停消费榜发奖任务、关闭双十一对卡网的发卡。否则两边会同时发卡和发奖。
2. 部署本版本（迁移 `275_native_shake.sql` 自动执行）。`NATIVE_BOX_SERVICE_URL` / `NATIVE_BOX_CONNECTION_ID` 已不再使用，可以从环境里删除。
3. 在 `/admin/shake` 新建活动，配置规则和奖池，确认后启用。
4. 如有双十一活动，把“目标摇摇卡活动 ID”改成新活动 ID 后重新保存。`activity_campaign_rewards.delivered_at` 已有值的任务（已在卡网发过卡）不会重新发放；尚未发放的任务会改为在 Sub 里发卡。
5. 如需消费榜发卡，先在消费榜设置里配置结算周期并开启自动奖励，再在摇摇乐后台绑定。
6. 需要补偿的用户用“手动补发”。
