# 多分组拒绝与模型日志缺失排查（2026-09-19）

基线：`v0.2.6-custom.1`（`0c607dd5e`）。修复分支：`fix/multigroup-routing-diagnostics`。

## 生产证据与结论边界

日本站实际运行版本为 `0.2.6-custom.1`。只读检查找到与用户提供的分组 3、25、27、48 拒绝信息完全匹配的 `/v1/responses` 错误；客户端为 Codex VS Code，数据库的 `model`、`requested_model` 均为空。

该错误发生在分组预检，尚未进入提供方处理器。模型日志缺失不代表客户端没有传模型，也不能证明模型解析为空。历史日志没有保留请求体，不能从相邻成功请求推定失败请求的模型或工具声明。

## 已复现并修复

1. **提前拒绝漏记模型。** 分组解析器已取得请求模型，但错误日志上下文原本由后续处理器填写。预检直接返回 503 时，模型与流式标记未写入。现在在分组准入之前记录客户端模型；保留映射前的名称，WebSocket 以首帧为准，握手查询参数不作为最终模型。
2. **Codex 被动图片工具声明被误判为生图。** 在一个支持请求模型、允许文本调用但关闭生图的 OpenAI 分组中，普通文本请求通过；只增加被动 `image_gen` namespace 声明，旧预检即返回不可用。正式 Responses 处理器已使用显式生图意图检查，预检仍用宽泛检查。现在预检对走 OpenAI Responses 处理器的平台采用同一规则，真正的图片工具和显式图片选择仍被权限门拒绝。

第二项与生产客户端类型及分组 3 关闭生图的配置吻合，但没有原请求体证据，不能认定它就是该条历史 503 的唯一原因。其他分组是否支持该模型也不能凭缺失的模型字段判断。

## 回归验证

- 路由器单测：探测收到正确模型，但旧版本日志上下文为空；修复后通过。
- 真实鉴权 → 分组拒绝 → 错误日志 → 日志仓库输入：覆盖 Responses 流式/非流式、未传模型、Gemini URL 模型。
- WebSocket：忽略握手模型提示，首帧拒绝保留模型及流式标记。
- 真实预检/调度服务：文本请求及被动 namespace 可用；原生图片工具、显式图片选择仍被拒绝。
