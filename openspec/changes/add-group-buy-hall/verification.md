# 拼团月卡验收场景

状态：已实现并完成本地功能、数据库事务、页面、全量单元/集成测试、代码检查与构建验证。规则来源：[design.md](design.md)；页面来源：[ui-design.md](ui-design.md)。

| 编号 | 场景 | 预期行为 |
| --- | --- | --- |
| V01 | 独购示例 198 元商品 | 支付成功生成独立卡号，基础总额 940、周限额 235，有效期精确为付款时刻后 30 天；同组旧卡的到期时间不被延长 |
| V02 | 同一用户参加两个不同团 | 同一分组产生两张卡，各自额度和起止时间独立；同一用户重复参加同一团失败 |
| V03 | 发起人付款后其他人陆续加入 | 发起人付款成功创建团并起算配置的招募期；各参与者付款后立即获得卡及当前档位额度，满团提前关闭招募 |
| V04 | 人数为 1/2、3/5、6/9、10 | 示例每卡总额依次为 940、960、1000、1100；人数只统计不同的成功付款参与者 |
| V05 | 本周已用 235，从两人升至六人 | 每张相关卡总额升至 1000、周上限升至 250，该用户本周可再用 15，已用量、周期和到期时间不变 |
| V06 | 卡在周三 15:00 付款 | 下一周三 15:00 重置，未用周份额不叠加；月累计已用量保留 |
| V07 | 1100 卡进入第 29 天，月剩 300 或 100 | 最后两天分别最多可用 275 或 100；到期后不准入新调用，不会因第五个周周期突破总额 |
| V08 | A 卡排在 B 卡前，A 周额度耗尽后恢复 | 暂时跳过 A 使用 B；A 下周恢复后重新优先；该分组的多个 API Key 共用顺序和用量 |
| V09 | 一次调用费 3，A 可用 1，B 可用 10 | 同一调用在 A 扣 1、B 扣 2，账户余额不重复扣款；日志保留两条卡分摊 |
| V10 | 一次调用费 3，仅一张卡可用 1 | 卡扣 1，按正常调用费用口径从余额补扣 2；所有扣费明细合计等于实际费用 |
| V11 | 卡全部不可用但账户有正余额 | 拒绝该订阅分组的新调用，余额不能替代可用订阅权益；账户充值与查看信息仍可用 |
| V12 | 卡剩 1、余额 0.5，已开始调用费 3 | 卡扣 1，余额变为 −1.5；该账户后续调用被阻止，即使其他卡有额度；结清后按通常权益准入恢复 |
| V13 | 并发调用竞争同一张卡的剩余周额度 | 卡在该周期的累计扣费不超上限，整卡累计不超总额；差额扣余额，已在途请求继续据实结算，可能扩大欠费 |
| V14 | 同一付款通知或计费请求重复投递 | 同一支付不重复生成卡或增加人数，同一调用不重复扣卡或余额；失败重试不能留下半笔分摊 |
| V15 | 周三 14:59 调用，15:00 重置，15:01 完成 | 结算计入调用开始时各卡的旧周期，下一周额度不被挪用，历史周期仍受其上限及整卡总额限制 |
| V16 | 调用开始时卡有效，结束前卡过期；途中又购卡或改排序 | 已开始调用按开始时的卡、顺序和周期结算；新卡和新排序只影响后续新调用 |
| V17 | 招募到期仅四人或八人 | 卡分别保留 960 或 1000；停止加入且不自动退款，用户继续使用剩余有效期 |
| V18 | 管理员批准一位成员退款 | 退款成功撤销对应卡，其他成员已有额度不回收，后续升档人数排除退款成员，已关闭的团不重新开放 |
| V19 | 团已关闭或无名额时到账且无法入团 | 原路退款，不能静默改为其他团或独购；退款结果和重试状态可查询 |
| V20 | 修改商品价格、额度、人数上限或招募期 | 仅影响新团；老团的后来参与者按老团规则付款和获得权益；已有卡不被配置改写 |
| V21 | 用户同时拥有旧订阅和新月卡 | 我的订阅统一展示，旧权益保持原额度、期限、重置规则，参与同组排序；旧内嵌销售及履约不被本功能自动关闭 |
| V22 | 拼团大厅处于四人团 | 卡片显示人数 4/10，当前额度 960、下一档 1000，距六人档还差 2 人；与距离满团还差 6 人区分 |
| V23 | 当前用户已经参团，或团由招募中变为满团/截止 | 已参团用户不能再次购买该团；招募列表不保留已结束团，原团号仍能查看状态和历史详情 |
| V24 | 访问我的订阅和现有购买页 | 每张卡单独展示并可调整顺序；原购买页的“订阅”页签变为“拼团”，含单独购买和开团，充值流程可用 |
| V25 | 持有同组旧卡后打开新月卡商品或原订阅深链接 | 页面正确落入新拼团购买区域并展示明确的购买方式，不因已有同组订阅而把新卡购买解释为延长旧卡期限；顶部摘要与独立卡实际额度一致 |

## 审查修复

独立只读审查发现并修复：请求中途改绑 Key 导致费用丢失、旧订阅同日手动重置额度被历史记录抵消、卡与旧订阅数值 ID 重合的错误标签，以及退款中断/渠道成功响应丢失后的恢复。退款恢复先查询渠道，渠道尚未处理时仅对有稳定幂等号的适配器重发；不支持查询的渠道提供后台人工核实入口，必须填写原渠道退款流水或说明并确认全额退款，操作留审计。

审查者最终复核：无剩余 Critical/Important 问题。档位详情按实施约定展示当前档位与规则，不提供事件时间线。

## 当前边界及发布门槛

- 示例 198 元商品由管理员选择真实订阅分组后配置；不向用户现有数据库自动添加示例商品或修改旧订阅。
- 批量生图沿用既有独立余额预冻结计费；是否纳入月卡已提出补充范围问题，尚未收到用户选择。普通图片、视频和文本走已实现的月卡结算。
- 原 OpenAI live 功能目前自身结算为零；本次只修正虚拟订阅 ID 的日志外键，不声称完成原 live 计费功能。
- Grok 视频维持已有“查询发现完成后结算”的触发方式。数据库在费用发生后、首次命令持久化前完全不可用的情况仍会报错；单靠同一故障数据库无法保证这一窗口的费用持久化。
- 新迁移保留旧订阅表的唯一约束，新卡不写旧订阅记录。旧版本回滚不会自动理解新卡权益；发布时应明确停售新卡及回滚期间新卡调用的处理方式，不能把结构兼容误称为功能兼容。
- 未进行真实支付渠道交易、CI、staging 或生产部署。工作区未提交、未推送、未打标签。

发布验证遵守用户提供的更新与灾备手册，涉及迁移时检查旧程序与新数据兼容性，先完成本地和 CI 验证、中国 staging 验收，再准备生产切换；生产单独确认、重新备份并保留回滚方案。
