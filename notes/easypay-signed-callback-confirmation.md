# EasyPay 回调确认兼容与安全修复

当前实现基于 `b28398552`（`0.2.17-custom.1`），尚未切换生产。

## 后台使用

在系统设置的支付服务商管理中编辑对应易支付实例，选择“回调确认方式”：

- **验签＋上游查单（默认）**：旧配置缺省仍走此模式，查单异常返回 502，绝不自动降级。
- **仅验签回调**：可信渠道无法提供查单时，由管理员明确选择；跳过回调中的额外查单，后续本地订单校验及事务入账不变。

字段存放于已有渠道配置 `notificationConfirmMode`，允许 `upstream`、`signed_callback` 和代表默认值的空值；无数据库迁移。后台拒绝未知值。设置也适用于已有订单的后续回调，可在查单失败后更改模式并让渠道重试真实通知。商户号和密钥的在途订单保护保留。

该选项仅影响回调的查单确认，不修改已有订单查询、取消、到期及退款逻辑。不支持查询的渠道丢失通知后仍需人工对账。已过余额订单到期宽限的订单，应单独核实、按现有业务恢复流程处理，不能把空回调的 HTTP 200 当作入账成功。

## 保留与加强的边界

- 配置接口仅供管理员使用，用户下单和回调参数不能选择确认模式。
- 使用订单绑定实例的密钥验签，检查 PID；仅验签成功通知必须包含外部订单号、渠道交易号和金额。
- 拒绝未知回调字段、重复字段及关键 token 的分隔符注入，保留付款链接签名不能充当付款通知签名的防护。
- 本地校验订单存在、渠道身份和应付金额；非有限数、零、负数、金额不匹配不会入账。
- 原子订单状态转换、履约租约和兑换码与余额事务共同保证重复及并发通知只入账一次；已退款状态不会因通知重放再次充值。
- 修复既有 `sub2_N` 兼容路径：只有数据库中外部订单号为空的真实旧订单可按 ID 解析；现代订单必须精确匹配外部订单号。提供方选择和履约共用同一解析，旧订单也绑定原渠道。

仅验签模式依赖渠道只在真实付款后正确签发通知，以及商户密钥保密。测试可验证已知攻击路径，不能提供“任何情况下绝无漏洞”的保证。测试和生产渠道应使用不同商户凭据。

## 验证

- 提供方、支付服务、回调及后台支付相关 `unit` 测试。
- PostgreSQL 全量迁移后的真实 HTTP→验签→履约→余额事务测试，启用 Go race detector；24 个并发 GET/POST 通知和重复重试只增加一次应得余额。
- 同一真实签名测试通知：默认模式遇 HTML 查单响应返回 502、余额不变；管理员切换模式后原通知重试可入账，不再发出确认查单。
- 覆盖金额篡改、错误商户/密钥、缺少签名/交易号、未知订单、NaN/Inf/零/负数、重复参数、客户端模式注入、非成功通知、付款链接重放、跨订单重放及退款后重放。
- 旧订单别名测试曾在修复前复现错误入账，修复后不再触发；另有无需 PostgreSQL 的单元回归测试。
- 后台控件缺省值、保存与两种模式互切、中文/英文选项、类型检查、前端构建及修改文件 lint。

独立 PostgreSQL 验证（只使用允许 CREATEDB 的测试服务器，测试自动创建并删除自己的数据库）：

```sh
cd backend
PAYMENT_WEBHOOK_TEST_DSN='<独立测试 PostgreSQL URL>' go test -race ./internal/handler -run '^TestEasyPayWebhookSecurityPostgres$' -count=1
```

## 发布边界

当前只完成本地实现与验证；真实支付渠道回调、GitHub CI、中国 staging 及美国生产切换尚需按发布流程验收。部署前备份当前运行程序和数据库；容器镜像标签可能早于网页更新后的程序版本，不能据此重建旧程序。保持新旧版本默认查单行为，不自动切换任何支付实例；启用兼容模式时仅选择目标实例。
